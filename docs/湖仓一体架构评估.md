# Gemini Quant Agent 湖仓一体架构评估

## 结论

项目需要采用“湖仓兼容”的数据架构，但现阶段不应立即部署完整的 Hadoop、Spark、Iceberg 集群。当前规模和在线交互方式更适合保留关系数据库作为事务与服务层，增量增加对象存储、Parquet 分层、统一目录和血缘。达到容量或并发阈值后，再将离线分析表升级为 Iceberg/Delta Lake。

这不是一次替换现有数据库、知识图谱或知识库的重构。现有成果继续承担在线服务，新架构先解决原文留存、批量分析、可重复治理和 KG/RAG 身份一致性。

## 当前能力

| 能力 | 当前实现 | 判断 |
| --- | --- | --- |
| 股票及公司主数据 | 关系数据库、统一证券/公司标识 | 可继续作为权威服务层 |
| 行情、财务和资讯 | 结构化业务表及同步日志 | 适合在线查询，缺少历史分层文件 |
| 公司关系 | 主体、证券映射、事实、证据与审核状态 | 模型合理，继续增量治理 |
| 非结构化资料 | 新闻、公告、F10、研报及公司披露存于数据库 | 可追溯，但大正文会挤占事务库 |
| 知识图谱 | 属性表投影、统一身份、证据边 | 现阶段无需强制迁移 Neo4j |
| RAG | 已有知识文档和治理框架 | 缺少统一切片版本、对象 URI 和向量索引契约 |
| 数据治理 | 数据资产、知识库、Skill/Agent、任务记录 | 已有基础，缺少跨层血缘和质量发布门禁 |

## 主要缺口

1. 原始响应、PDF、HTML 和大 JSON 没有统一的不可变对象存储地址、内容哈希和保留策略。
2. 缺少 Raw、Normalized、Serving 三层物理数据集，以及按交易日、市场和来源分区的 Parquet 快照。
3. 关系数据库中的在线事实与 RAG 切片、图谱节点之间尚未形成统一的数据版本和血缘记录。
4. 缺少 schema contract、质量检查结果、发布批次和可回放治理任务的统一目录。
5. 分析查询仍可能直接扫描在线表；规模增长后会影响接口延迟。

## 目标架构

```text
外部数据源
  -> Raw/Bronze：原始响应、PDF、HTML、JSON（MinIO/S3，内容寻址）
  -> Normalized/Silver：标准化 Parquet（证券、公司、行情、财务、披露、关系候选）
  -> Curated/Gold：指标快照、特征、已审核关系、RAG 切片、发布数据集
       |-> PostgreSQL：主数据、审核事实、任务状态、在线接口
       |-> pgvector：可追溯的文档切片向量
       |-> KG 投影：当前属性表；规模和遍历压力达到阈值后评估 Neo4j
       `-> DuckDB/Polars：研究和批量质量分析
```

所有层使用同一组 `canonical_security_id`、`canonical_company_id`、`document_id`、`content_hash`、`dataset_version` 和 `observed_at`。图谱关系及 RAG 回答必须能回到对象存储原文和来源记录。

## 分阶段实施

### 第一阶段：湖仓兼容，不迁移在线库

- 增加对象存储适配层，开发环境可使用本地目录，生产使用 MinIO/S3。
- 为原始资料登记 `object_uri`、`content_hash`、媒体类型、来源时间、采集批次和解析状态。
- 增加 Raw/Normalized/Serving 数据集目录及质量结果表。
- 用 Parquet 输出行情、财务和文档元数据快照，DuckDB/Polars 承担离线分析。
- RAG 切片保存原文偏移、解析器版本、嵌入模型版本和主数据标识。

### 第二阶段：形成开放表格式

当单表达到数千万至亿级记录、需要频繁回溯修订或多任务并发写入时，引入 Iceberg。元数据目录可选择 REST Catalog；计算仍可从 DuckDB/Polars 起步，确有分布式需求后再增加 Spark/Trino。

### 第三阶段：按负载拆分服务

- 在线事务迁移至 PostgreSQL，SQLite 仅保留本地开发。
- 向量检索优先使用 pgvector；向量规模或召回压力超出其能力后再独立部署向量数据库。
- 图遍历深度、节点量和并发达到明确阈值后再评估 Neo4j，不把它作为原始文档或事实主存储。

## 启动与升级门槛

现在应启动第一阶段。出现下列任一情况再进入第二阶段：单类行情超过 5,000 万行；数据库文件持续超过 100 GB；需要跨版本时间旅行；每日批处理超过单机维护窗口；多个计算任务需要并发读写同一历史数据集。

## 风险控制

- 不双写无校验：每次落湖和入库使用同一批次号并校验行数、哈希及主键范围。
- 不把候选线索发布为事实：LLM 抽取进入候选层，只有来源规则或审核流程可发布到 Serving/KG。
- 不复制身份规则：证券和公司 ID 由现有主数据服务生成，湖仓只引用。
- 不一次迁移：先旁路归档和快照，验证恢复、查询和血缘后再迁移历史正文。

## 建议决策

批准“第一阶段湖仓兼容层”，暂缓完整 Iceberg/Spark 平台。下一项工程应先定义对象存储与数据集目录契约，并选择 MinIO/S3 部署方式；这一步可以独立交付，也不会影响当前接口和图谱。

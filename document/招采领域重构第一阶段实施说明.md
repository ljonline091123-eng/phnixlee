# 招采领域重构第一阶段实施说明

## 本阶段已落地

本阶段采用增量旁路建模，未删除旧表和旧接口，新增以下业务对象：

| 对象 | 中文释义 | 业务职责 |
|---|---|---|
| `BidSubmission` | 投标提交 | 一个供应商针对一个招标公告的投标聚合根 |
| `BidSubmissionVersion` | 投标版本 | 首次报价和每次调价形成的不可变版本 |
| `EvaluationAssignment` | 评标任务 | 专家参与某次招标评标的任务实例 |
| `EvaluationSheet` | 评标表 | 专家针对一个投标版本提交的评分结果 |
| `AwardDecision` | 定标决策 | 采购方对评标结果做出的定标决策 |
| `AwardCandidate` | 中标候选人 | 定标前的候选人和综合排名快照 |
| `AwardPublicity` | 中标公示 | 定标后的公示内容和公示期 |

领域对象内置了状态行为：

- 投标提交：草稿 → 已提交 → 可撤回；
- 评标任务：待处理 → 进行中 → 已完成；
- 定标决策：草稿 → 已定标 → 已公示；
- 公示：校验结束时间晚于开始时间后才允许发布；
- 评标表：提交时自动计算商务、技术、报价总分。

## 数据库迁移

迁移脚本为：

`document/sql_update/2026.09.22招采领域对象规范化.sql`

该脚本只创建新表，并没有自动修改生产数据库。执行前必须对目标数据库做一致性备份，执行后再通过适配服务将现有 `tb_bidding_info`、`tb_expert_score`、`tb_bidding_result` 数据逐步迁移到新对象。

## 后续接入顺序

1. 在投标提交服务中双写 `tb_bid_submission` 和 `tb_bid_submission_version`，验证版本号唯一性。
2. 将专家任务页面从 `tb_bidding_evaluat_expert` 读取迁移到 `tb_evaluation_assignment`。
3. 将专家评分从 `tb_expert_score` 迁移到 `tb_evaluation_sheet`，保留旧查询适配层。
4. 将 `BiddingResult` 查询改为 `AwardDecision`、`AwardCandidate`、`AwardPublicity` 三表聚合。
5. 完成历史数据校验后，再下线旧字段的写入逻辑。
